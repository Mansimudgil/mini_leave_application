# 🏖️ TimeOff HQ — Mini Leave Request & Approval Application

A modern, full-stack leave management application built with **Node.js, Express, MongoDB (Mongoose), and React (Vite)**. Designed with enterprise-grade edge case handling, real-time date calculation, balance tracking, and an intuitive dual-portal interface for Employees and Managers.

---

## 📋 Features

- 👤 **Employee Portal**:
  - View real-time Casual Leave and Sick Leave balances with animated progress bars.
  - Interactive **Apply for Leave** modal with instant calendar vs. working days breakdown.
  - View personal leave history and manager review comments.
  - Switch between sample employee profiles to test different balances and departments.

- 🛡️ **Manager Portal**:
  - Central dashboard showing pending approvals, approved leaves, and rejected leaves.
  - One-click **Approve** (with automated balance deduction) and **Reject** actions.
  - Optional manager feedback/reason modal for transparent audit trails.
  - Full organization-wide leave history log.

---

## 🛠️ Tech Stack

- **Backend**: Node.js & Express.js
- **Database**: MongoDB (via Mongoose ODM)
  - Supports **MongoDB Atlas** (cloud free tier), local MongoDB daemon, and an automatic **zero-config in-memory MongoDB** fallback so anyone can clone and run immediately without database setup.
- **Frontend**: React 18, Vite, Vanilla CSS Design System (curated HSL color palette, dark mode glassmorphism, responsive tables).
- **Icons**: Lucide React
- **Testing**: Built-in automated end-to-end test suite (`server/test_e2e.js`).

## 🎯 Edge Cases Handled & Business Rules

### 1. Weekend Handling Policy
* **Approach**: Standard corporate working days policy.
* **Mechanism**: Saturdays (day 6) and Sundays (day 0) are recognized as official non-working days.
* **Working Day Calculation**: When an employee requests a leave spanning across a weekend (e.g., Friday to Monday = 4 calendar days), only the **2 working days** (Friday and Monday) are counted and deducted from their balance.
* **Weekend-Only Date Range**: If an employee selects a date range consisting strictly of weekend days (e.g. Saturday to Sunday), the deductible working days is `0`. The system explicitly blocks submission with HTTP 400: *"The selected date range contains only weekend days (Saturday/Sunday). Leaves are not required on non-working days."*
* **Live Transparency**: The frontend modal displays a live day-by-day chip breakdown indicating which days are counted and which are skipped.

### 2. Overlapping Leave Requests
* The backend queries all existing leaves for the applicant with status `Pending` or `Approved`.
* Using the range overlap condition `(startDate <= existing.endDate && endDate >= existing.startDate)`, any conflicting date range is rejected with a descriptive message indicating the conflicting leave dates and status.

### 3. Insufficient Leave Balance
* **At Submission**: Calculated working days are checked against the employee's current balance for the selected leave type (`Casual` or `Sick`). Requests exceeding available days are blocked immediately with an `INSUFFICIENT_BALANCE` error.
* **At Approval**: Balance is re-verified when a manager clicks "Approve" to guard against concurrent race conditions before executing the deduction.

### 4. Deduction Upon Approval Only
* As required, leave balances remain untouched while requests are in `Pending` status.
* Quota is deducted strictly when a manager marks the request as `Approved`.
* If a request is `Rejected`, no balance is deducted.

### 5. Idempotent Review Lock
* Requests already marked `Approved` or `Rejected` cannot be reviewed again, preventing duplicate deductions.

## 🤖 AI Tools Disclosure & Reflections

### 1. Which AI Tools Were Used & For What
- **Google DeepMind Antigravity / Gemini 3.8 Flash**:
  - Full-stack architectural scaffolding (Express REST API + React Vite client).
  - Designing responsive CSS design system and interactive components.
  - Implementing the date calculation algorithm and automated test runner.
  - Diagnosing environment configurations and test automation.

### 2. What Was Generated by AI That Was Incorrect or Changed & Why
- **Date Timezone Shift Bug (`toISOString()` Trap)**:
  - *Initial Generated Code*: The utility that constructed the day-by-day breakdown used `current.toISOString().split('T')[0]`.
  - *The Problem*: In any timezone east of UTC (e.g., UTC+5:30 IST), parsing `2026-10-02T00:00:00` into a `Date` object and converting it to ISO string (UTC) shifts the timestamp back 5.5 hours to `2026-10-01T18:30:00.000Z`. Consequently, the date string became `2026-10-01` instead of `2026-10-02`, corrupting the day-by-day breakdown and causing Saturday/Sunday detection to misalign by 1 day!
  - *The Fix*: Refactored date string generation to use explicit local date component methods (`getFullYear()`, `String(getMonth() + 1).padStart(2, '0')`, `String(getDate()).padStart(2, '0')`), ensuring calendar dates remain invariant regardless of the host server or client timezone.
- **Handling Zero-Working-Day Requests**:
  - *Initial Output*: The initial formula simply computed `workingDays = 0` and permitted the submission since `0 <= balance`.
  - *The Change*: Added explicit validation to block requests where `workingDays === 0` (e.g. ranges solely on Saturday/Sunday), preventing redundant records in the database.

## 💻 Instructions to Run Locally

### Prerequisites
- [Node.js](https://nodejs.org/) (v18 or higher recommended; developed on v22)
- npm (v9+)

### Quick Start (Single Command)

1. **Clone the repository**:
   ```bash
   git clone <YOUR_GITHUB_REPO_URL>
   cd leave_application
   ```

2. **Install all dependencies** (root, server, and client):
   ```bash
   npm run install:all
   ```

3. **Start both backend and frontend concurrently**:
   ```bash
   npm run dev
   ```

4. **Access the application**:
   - **Frontend UI**: [http://localhost:5173](http://localhost:5173)
   - **Backend API**: [http://localhost:5000](http://localhost:5000)
   - **API Health Check**: [http://localhost:5000/api/health](http://localhost:5000/api/health)

## 🌐 Deployment Guide (Free Hosting)

### 1. Database (MongoDB Atlas Free Tier)
1. Go to [MongoDB Atlas](https://www.mongodb.com/cloud/atlas) and create a free M0 cluster.
2. Under **Network Access**, add `0.0.0.0/0` (allow access from anywhere).
3. Under **Database Access**, create a user and copy the connection string:
   ```text
   mongodb+srv://<username>:<password>@cluster0.mongodb.net/leave_management?retryWrites=true&w=majority
   ```

### 2. Backend Deployment (Render / Railway / Zeabur)
1. Connect your GitHub repository to [Render](https://render.com/) or [Railway](https://railway.app/).
2. Set Root Directory to: `server`
3. Build Command: `npm install`
4. Start Command: `npm start`
5. Add Environment Variables:
   - `MONGODB_URI`: your MongoDB Atlas connection string
   - `PORT`: `5000` (or host assigned)
   - `NODE_ENV`: `production`

### 3. Frontend Deployment (Vercel)
1. Connect your GitHub repository to [Vercel](https://vercel.com/).
2. Set Root Directory to: `client`
3. Framework Preset: `Vite`
4. Add Environment Variable:
   - `VITE_API_URL`: Your deployed backend URL (e.g. `https://your-api.onrender.com`)
5. Click **Deploy**.
